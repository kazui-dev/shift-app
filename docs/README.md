## 文書の扱い

### 現在の説明

手順・構成・スキーマの文書は対象の変更に合わせて更新する。未実装の案で現行の説明を上書きしない。要件にも、合意と実装の状態を混同させない。

同じ仕様を複数の文書へ丸ごとコピーしない。詳細の置き場所を決め、他からはリンクする。過去の版はGitで追えるため、更新のたびに日付付きコピーを増やさない。

### ADR

今後の設計・実装を制約する重要な判断を、1つの判断のまとまりにつき1文書で残す。会話全文、作業ログ、細かな文言調整、単なる実装手順をADRにしない。

- 配置は `adr/NNNN-short-title.md`。番号は再利用しない。
- 背景、決定、検討した選択肢、影響、関連資料を簡潔に記す。
- 状態は「提案中」「採用」「却下」「置換済み」で区別する。「採用」は実装完了を意味しない。
- 実装状況は別欄で示し、実装時に関連コードやPR・仕様文書へリンクする。
- 採用後の判断を変更する場合は新しいADRを作り、旧ADRに置換先を記す。以前の判断理由を新しい理由で上書きしない。
- 誤記・リンク・状態の更新は可能。保留中の詳細を、合意済みの決定として書き足さない。

### 設計ドキュメント

`design/` に変更の全体像・要件・挙動・未決事項をまとめる。設計の進展に合わせて同じ文書を更新し、過去の版はGitで追う。対話履歴専用のディレクトリは設けない。

合意済みの要件、提案、未決事項、実装状況を明記し、途中の案を確定仕様や実装済みの挙動と混同させない。重要な判断理由はADRへリンクする。

実装時に関連する現行文書を更新し、設計ドキュメントにも実装状況と参照先を記す。以後の仕様を現行文書と設計ドキュメントの両方で重複管理しない。

## 整理の根拠

- [Diátaxis](https://diataxis.fr/start-here/) は、手順・参照・説明など、読み手の目的に応じて文書の役割を分ける考え方を示している。
- [Diátaxisの適用指針](https://diataxis.fr/how-to-use-diataxis/) に従い、形式を満たすためだけの空の階層は作らない。既存の少数の文書を一律に移動する必要はない。
- [ADRのテンプレート](https://adr.github.io/adr-templates/) を参考に、判断の背景・決定・影響を記録する。以下のADRは本プロジェクト向けの簡潔な形式であり、特定テンプレートへの完全準拠を主張しない。
