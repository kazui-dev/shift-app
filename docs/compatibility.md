# 互換と変更の出し方

利用者がいる本番へ変更を出すときの区分と、一時的に残している互換の一覧。

## 変更の区分

サーバーは main への push で切り替わるが、画面は利用者が「更新」するまで古い版のまま動く。新しいサーバーと古い画面が同時に動いても壊れないか、戻せるかで分ける。

| 区分         | 対象                                                                                    | 出し方                                                                                             |
| ------------ | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| そのまま出す | 画面・ブラウザー側の処理・キャッシュの扱い、APIやイベントの追加                         | 変更量が多くてもよい。問題があれば Workers のバージョンを戻す                                      |
| 順番を守る   | API・WebSocket の URL 変更や削除、レスポンスの形の変更、必須項目の追加                  | サーバーが新旧両方を受け付ける → 画面を更新してもらう → 古い方を消す。残した互換は下の一覧へ載せる |
| 慎重に進める | D1 マイグレーション、Durable Object のクラス名、セッション・Cookie、VAPID 鍵、R2 のキー | スクリプト・バックアップ・実施時間を決めてから行う                                                 |

シフト当日・勤務時間中は、区分にかかわらずデプロイしない。

## シフト希望の変更履歴

希望の変更履歴と提出版は migration 0045 で追加する。既存の回答は現在値のまま保持し、過去の変更を推測して履歴へ入れない。同じ提出版に対する並行した再提出は後続を `SUBMISSION_CHANGED` で拒否し、履歴の変更前後を守る。migration を先に適用してから新しい Worker を出す。旧画面はレスポンスの追加項目を無視でき、新しい履歴 API は旧画面から呼ばれない。Worker を戻す場合もテーブルを残し、旧 Worker で行われた再提出の履歴は記録されない。

## 提出状況からの希望編集

migration 0047 を先に適用してから Worker と Web を更新する。既存の回答と履歴は保持し、過去の変更者は推測しない。履歴に変更者の ID と当時の表示名を追加し、名簿側にも変更履歴と提出版を持たせる。初回サインイン時は、既存の回答移行と同じトランザクションで名簿側の履歴も移す。本人の下書きには編集元の提出版を記録し、他の人による保存では書き換えない。

本人の保存 API は旧画面の `revision` 省略を暫定的に受け付ける。ただし、本人以外の変更履歴がある回答を版なしで提出した場合は `SUBMISSION_CHANGED` として拒否する。更新前の画面から古い回答で上書きさせず、画面の更新を必要とする。新画面は表示時の版を送信し、本人の古い下書きも提出時に競合として扱う。再読み込みを選ぶと最新の提出内容を読み直す。

Worker を戻しても追加列・テーブル・トリガーは残す。旧 Worker には表示時の版による競合検出がないため、戻している間はこの編集機能を使わない。端末の復旧用下書きも回答と提出版を一緒に保存する。旧形式の回答配列は失わないように読み取り、編集元を確認できないため版 0 として扱う。提出版が進んでいれば競合となり、最新回答へ混ぜない。

## シフト作成時の有効化と入力条件

新規作成・複製は責任者を保存した同じトランザクション内で有効にする。責任者が実メンバーに解決できなければ全体を取り消し、既存の `RESPONSIBLE_REQUIRED` エラーを返す。既存シフトの状態は変更しない。場所は空文字を許可する。

責任者の必須化は「順番を守る」に該当する入力条件の変更。HTTPのフィールド・レスポンス・エラー形式は維持し、更新前の画面でも責任者を指定すれば作成できる。指定しない場合は既存のエラー表示で選択を促す。場所の必須解除は入力制約の緩和で、新旧画面からの文字列をそのまま受け付ける。一時的な互換処理は追加しない。

## 2026年の外部アンケート回答と初回サインイン前の参加者

外部アンケートの回答者には初回サインイン前の人もいる。回答・割当は既存の `student_directory` に紐付けて保持し、認証用の `user`・`account`・`session`、`app_users`、`year_memberships` は事前作成しない。`app_users.user_id` はNOT NULLとする。

### 保存と表示

- `directory_availability_submissions` は名簿の回答を保持する。`submitted_at IS NULL` は全日未回答を表す。
- 年度から外す名簿行は削除せず `student_directory.status='inactive'` にする。回答は保持し、希望・配置候補と名簿サインインからは除外する。後日アカウントができてもその年度の回答・参加を自動で移さない。割当がある場合は先に取り消す。
- 旧サーバーは `status` を見ずに名簿サインインを照合する。`directory_inactive_member_guard` は、無効な名簿行の年度がデフォルトである間、その学籍番号での `app_users` 作成を DB で拒否する。新サーバーの名簿照合は `active` の行だけを通す。このガードを撤去するときは、稼働中の旧サーバーがないことを確認して新しい migration で削除する。
- `directory_availability_day_answers` と `directory_availability_windows` は確定できた日の回答・参加可能時間を保持する。判断できない日は行を作らず未回答とする。
- `directory_shift_assignments` は名簿の人への割当を保持する。実メンバーの希望・割当は従来のテーブルを使う。
- 希望確認・シフト編集・割当数では `apps/api/src/features/directory/services/directory-work.ts` の集計用SQLで双方を読む。提出判定は日別回答と受付日程の版による。
- メンバー一覧・年度参加・チャットは従来どおり実メンバーのみを扱う。未サインインの人を除外する処理や認証状態のUI表示は追加しない。
- HTTPのレスポンス形式は維持する。名簿IDはUUIDのバージョン・variantを保証しないため、HTTPの対象IDには使わない。名簿側では回答レコードのUUIDを既存の `memberId` として返し、保存時に名簿IDへ解決して対応するテーブルへ書き分ける。更新前クライアントのUUID検証も維持する。

### 初回サインイン

名簿照合など既存の本人確認を通過すると、通常どおり実メンバーを新規作成する。
DBトリガー `directory_work_on_registration` はこの作成と同じトランザクションで、学籍番号が一致する名簿の希望・割当を新しいメンバーIDへ移し、名簿側の作業データを削除する。回答・割当のIDは保持する。認証方式には依存しない。
年度参加を作り、影響する年度のシフトの版を上げるため、移行前の対象IDを持つ古い編集画面からの保存は競合として再取得になる。
名簿サインインの初回は従来どおり `created: true` でアイコン設定へ進み、2回目以降は `false` となる。

### 変更の出し方

DB変更を伴うため「慎重に進める」に該当する。0040で名簿用テーブルとトリガーを追加し、対象データを移した後、0041で `app_users.user_id` のNOT NULLを適用して対応サーバーを出す。
0041は認証のないメンバーが残っていると失敗する。適用前に0件であることを確認する。名簿側にデータがある間は、それを読めないサーバーへ戻さない。
取り込み・名寄せ・個別データ移行の処理と回答原文はリポジトリへ置かない。個人データの保全と復旧方法は本番の操作ごとに確認する。

### 削除条件と手順

`directory_availability_*` / `directory_shift_assignments` テーブルがすべて0件で、本人のサインイン後にも希望・割当が保たれていることを確認できたら削除できる。サインインしない人が残った場合は、その人の記録をどう扱うか決めるまで残す。日数だけでは外さない。

1. `apps/api/src/features/directory/services/directory-work.ts` のSQLを呼ぶ `apps/api/src/features/activities/services/activity-editor.ts`、`apps/api/src/features/shifts/services/save-shift-plan.ts`、`apps/api/src/features/availability/routes/years/availability-submissions.ts`、`apps/api/src/features/activities/routes/years/activities.ts` を実メンバーのテーブルだけ読む形へ戻す。
2. 名簿用の保存分岐、上記集計用SQL、対応する回帰テスト・テスト補助を削除する。
3. 新しいマイグレーションで `directory_work_on_registration`・`directory_assignment_check`・`directory_slot_overlap` と名簿用テーブルを削除し、`packages/db/src/schema/availability.ts` と `schema/shifts.ts` からも定義を除く。既存の年度参加作成トリガーの重複防止条件は見直す。
4. 実メンバーの希望確認・割当保存・初回サインインを検証し、この節と互換一覧の行を削除する。適用済みマイグレーションは削除・編集しない。

## 変えない識別子

互換で吸収できないため、名前が実態に合わなくなっても変更しない。

- Durable Object のクラス名 `ChatRoom`・`ChatDirectory`。`ChatDirectory` はチャット以外の変更通知も配る
- binding 名、適用済みの D1 マイグレーション

## D1 読み取り範囲の削減（0048–0049）

0048は時間枠の索引、0049は責任者ビューと責任者喪失トリガーを変更する。データ移行や削除はなく、HTTP・WebSocket・保存済みIDの契約は維持する。新旧クライアントで同じレスポンスを使える。migrationを先に適用し、その後Workerを出す。

Workerだけ戻しても新しい索引・ビュー・トリガーは旧SQLから利用できる。DBも戻す場合は0048の索引を削除し、0049で置き換えたビューと8トリガーを0020の定義に戻す新規migrationを作る。既存migrationの編集やデータの巻き戻しはしない。0049適用時に既存活動のactive/versionは書き換えない。

## 通知の送信者表示と既読連動

Push payloadに任意の`icon`と`data.roomId`・`data.sequence`を追加する。旧Service Workerは追加項目を無視でき、新Service Workerも旧payloadを表示できる。メッセージ番号のない旧通知は既読判定で消さない。新Service Workerからの画面移動要求に旧クライアントが応答しない場合は別ウィンドウを開く。DB migrationは不要。

## シフト編集の日別回答

編集応答に `availabilityAnswers`（現行版の日別提出回答）を追加する。旧画面用の `submittedMemberIds` は維持する。保存入力とDBは変更しない。WebとAPIは同時に配信し、更新前の画面は追加項目を無視できる。

### シフトチャットの勤務割当条件（2026-10-07）

シフトに紐づくチャットの一般メンバー権限には有効な勤務割当を必須とする。HTTP・WebSocketの形式とDB構造は変更せず、既存クライアントにも同じ認可を適用する。権限を失った直接アクセスは既存の404を返す。シフト管理者・システム管理者のアクセスは維持し、暫定互換やmigrationは追加しない。

## 全体シフト一覧（2026-10-16）

`GET /api/years/:year/shift-overview?date=YYYY-MM-DD` を追加する。管理者は年度全体、責任者は担当シフトの情報だけを取得でき、一般スタッフは取得できない。編集は既存のシフト保存 API と版による競合検出を利用する。既存 API・保存形式・イベント形式は変更せず、DB migration は不要。「そのまま出す」に該当し、Worker を戻しても保存データは維持される。既存の勤怠記録を表示し、予定終了時刻から退勤済みを推定しない。

## シフト表のメンバー補足表示

個別シフトと全体シフト一覧のレスポンスの `roles` に、担当ロールを識別する `duty` を追加する。既存画面は追加項目を無視でき、DB・保存要求は変えない。新画面と Worker は同時に配信し、戻す場合も両方を戻す。

## 全体シフトの下書き保存・複製時刻（2026-10-20）

全体一覧の編集はブラウザー上の下書きに保持し、保存時に変更のあるシフトだけを既存 PUT API で保存する。最新の版に下書きの差分を重ね、編集したメンバーの当該シフト内の勤務時間は今回の編集を優先する。他メンバーの勤務とシフト設定は最新の内容を保つ。版の競合は最大 3 回まで再取得して試行する。複数シフトは順に保存し、一部の失敗時は未保存分を残す。全件一括の原子性は保証しない。保存完了分は再送しない。DB・保存 API の形式は変更しない。

複製 API に任意の startsAt / endsAt を追加し、旧画面の date のみの要求も受け付ける。新画面は複製先の日付と開始・終了時刻を指定する。名前・場所・種類・色・備考・対象ロール・責任者・必要人数・空の時間枠を引き継ぎ、配置メンバーと勤怠は引き継がない。時間枠と必要人数は開始時刻の差だけ移動し、指定範囲外を切り詰める。終了時刻が開始時刻以前の場合、新画面では翌日終了として扱う。DB migration は不要。

## 勤務配置の一括操作（2026-10-22）

対象の選択後に一括割当・割当解除を表示し、解除は既存のシフト保存APIで下書きを保存する。全体一覧では複数シフトの下書き変更を1回の取り消し単位にまとめる。HTTP・WebSocket・保存形式を変えず、DB migrationは不要。旧画面も同じAPIを利用でき、WorkerとWebを戻しても保存済みデータは維持される。「そのまま出す」に該当する。

## シフトの重要な連絡事項（2026-10-26）

0050で`activity_notices`を追加してからWeb・Workerを配信する。既存データの変更・削除はない。Workerを戻しても連絡事項はDBに残り、旧Workerは参照しない。テーブルは戻さない。

シフト編集の入力・応答に任意の`notices`、本人の勤務応答に任意の`notices`を追加する。更新前の画面は追加項目を無視できる。保存時に省略された連絡事項は既存値を保持し、空配列だけが全件削除を意味する。シフト本体と同じ版・D1 batchで保存し、既存の`shifts_changed`で本人の勤務も再取得する。

一般メンバーへの応答は有効な年度参加・本人の有効な勤務割当・有効なシフトに限定する。チャット本文の転載、既読の記録、出勤前の確認チェックは追加しない。複製先には期間固有の連絡をコピーしない。

2026-10-28に表示期間の解釈を訂正した。本人の勤務応答には同じシフトの連絡予定を返し、Webは現在時刻が開始以上・終了未満の連絡だけを表示する。勤務や取得対象月との重なりでは絞らず、キャッシュ済みの応答でも期間境界で表示を切り替える。表示期間は画面の表示条件であり、本文のアクセス権を時間で制限するものではない。API・保存形式・DBの変更はない。旧画面には現在時刻の判定がないため、更新通知からWebを更新する必要がある。

## 年度別のメンバータグ（2026-10-28）

0051で `year_tags` と `member_year_tags` を追加してからWeb・Workerを配信する。既存データの変更・削除はなく、ロールや権限の扱いは変えない。タグの一覧・作成・名前変更・削除と、メンバーへの一括付与・解除は新しいAPIで提供し、既存の名簿応答は維持する。旧画面は追加APIを利用しない。

Workerを戻す場合も追加テーブルとタグのデータは残す。DBも戻す必要がある場合はタグデータを退避してから、新規migrationで `member_year_tags`、`year_tags` の順に削除する。適用済みmigrationは編集しない。

## 年度別の勤怠通知閲覧設定

0052は設定・ロール・メンバーの3テーブルを追加する。勤怠通知本文と `private_to`、Durable Objectの識別子・保存形式は変更しない。新コードは設定なしを本人のみとして扱う。既存年度を全員公開にする運用は `year_attendance_settings.notice_audience='room_members'` を明示保存して行い、新年度には継承しない。閲覧設定は過去の通知、未読、検索、画像、ライブ配信、今後のPushに共通適用する。設定変更時はaccess_changedを配信して履歴を含め再取得する。既に届いたPushや端末に取得済みの情報を遠隔で回収する機能ではない。

戻す場合は追加テーブルと設定を残し旧Workerを再配信できるが、旧コードは以前の責任者・管理者判定に戻る。旧クライアントは閲覧範囲の説明に「責任者」と表示する場合があるため、新コードの利用時は更新を案内する。

## 遅刻・欠勤の理由を必須化

遅刻・欠勤の新規送信・再送信は理由を必須とし、trim後1〜1000文字をWebとAPIで受け付ける。理由のない既存記録の読み込み、取り消し、出勤の操作は維持する。DB migrationは不要。旧Webの理由なし送信もAPIで422として拒否するため、更新して理由を入力する。ロールバック時は旧WorkerとWebを同時に戻す。
